- A short room name is looked up in the list `matrix-e2ee-cli rooms --json` prints (from the CLI's store, or from the watch daemon while it runs) instead of two or three HTTP requests per joined room, in the order of version 4. For `matrix-send.py`, `matrix-read.py`, `matrix-edit.py`, `matrix-invite.py` and `matrix-power-level.py`, which used `find_room_by_name` in version 5.0.0, that order differs: a single exact name now wins even when another room's name contains it (version 5.0.0 refused `test` beside `test-archive` for a room without alias), and several rooms with the same alias name are refused instead of taking the first. A listing that fails, or a warning that the members of a room could not be read, stops the command as a failed request did
- `matrix-rooms.py`, `matrix-resolve.py`, `matrix-create-room.py`, `matrix-invite.py` and `matrix-power-level.py` keep their usage and arguments and pass the output of matrix-e2ee-cli's `rooms`, `resolve`, `create-room`, `invite` and `power-level` through. A room is created unencrypted unless the homeserver's defaults encrypt it, as before
- `matrix-send.py`, `matrix-read.py` and `matrix-edit.py` keep their options and run the CLI's `send`, `read` and `edit`: encrypted in an encrypted room, unencrypted in an unencrypted one. `matrix-read.py` prints the messages newest first in the format of `matrix-read-e2ee.py`, decrypted where the device holds the keys. `matrix-edit.py` edits only your own messages
- `matrix-doctor.py` checks `admin_token` only; a leftover `access_token` gets a warning row and is never sent
