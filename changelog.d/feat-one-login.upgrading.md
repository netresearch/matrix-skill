- Breaking: the skill logs in once, with the matrix-e2ee-cli session (`matrix-e2ee-setup.py`). `matrix-send.py`, `matrix-read.py`, `matrix-edit.py`, `matrix-rooms.py`, `matrix-resolve.py`, `matrix-create-room.py`, `matrix-invite.py` and `matrix-power-level.py` run matrix-e2ee-cli instead of sending HTTP requests with the config's token, so `access_token`, `access_token_file` and `MATRIX_ACCESS_TOKEN` are no longer read by any script. A setup that has only an `access_token` and no E2EE device has to run `matrix-e2ee-setup.py` first; then remove the `access_token` from `config.json` (`matrix-doctor.py` warns while it is there, and names the skill's device when the token is that device's own)
- Breaking: matrix-administration no longer reads `access_token`, `access_token_file` or `MATRIX_ACCESS_TOKEN`. Its token comes from `MATRIX_ADMIN_TOKEN`, `admin_token_file` or `admin_token`, else from the access token of the matrix-e2ee-cli session, which is sent to the homeserver recorded in that session and works only when that account is a server admin. A session without a homeserver counts as absent; its token is never sent to config.json's homeserver. A set admin token still wins, even a dead one. Move a server-admin token kept in `access_token` to `admin_token`
- Breaking: a `matrix-watchd.py` started with matrix-e2ee-cli 0.3.0 answers the new requests (`rooms`, `resolve`, `create-room`, `invite`, `power-level`) with "unknown op", and the commands then stop instead of taking the direct path; that includes every lookup of a short room name. `matrix-read.py` and `matrix-read-e2ee.py` also go through the daemon while it runs (its `read` request, new in matrix-e2ee-cli 0.4.0), so they too need a daemon started from 0.4.0. Run `matrix-watchd.py --stop` and `--start` after the upgrade
- Breaking: `matrix-send.py`, `matrix-read.py`, `matrix-edit.py`, `matrix-rooms.py`, `matrix-resolve.py`, `matrix-create-room.py`, `matrix-invite.py` and `matrix-power-level.py` sent plain HTTP requests before and now need the matrix-e2ee-cli binary, downloaded on first use. Release builds exist for Linux on x86_64 and aarch64, macOS on x86_64 and aarch64 (Apple silicon), and Windows on x86_64 (`_lib/cli_release.json`); on any other platform build matrix-e2ee-cli yourself and set `MATRIX_E2EE_CLI` to that binary
- Breaking: `matrix-send.py --format text` exits 2 with an error instead of sending, because matrix-e2ee-cli always renders Markdown; drop the option
- Breaking: `matrix-invite.py` and `matrix-power-level.py --set` refuse a room name that matches only partially, like the other commands that write; pass the exact name, the full alias or the room ID
- Breaking: `matrix-send.py '#alias:server'` with an alias that does not resolve is an error; version 5.0.0 then looked the room up by the alias's local part. Pass a resolvable alias, the room ID or the name
- Breaking: `--debug` of `matrix-send.py`, `matrix-edit.py`, `matrix-invite.py`, `matrix-create-room.py` and `matrix-power-level.py` printed how the room and the request were resolved; it is now accepted and ignored, and `matrix-rooms.py`, `matrix-resolve.py` and `matrix-read.py` accept it too
- Breaking: a short room name (`ops`, `#ops`) without a matrix-e2ee-cli session stops the command with a hint to run `matrix-e2ee-setup.py`; version 5.0.0's E2EE scripts passed it on to the CLI unchanged. On a machine with a matrix-nio device the takeover runs first and creates the session, so the name is looked up after it
- Breaking: `matrix-doctor.py` exits 1, also with `--json`, when the matrix-e2ee-cli session is missing or the homeserver rejects it, because every script needs that session now; an unchecked session (`--offline`, a pending takeover) still fails nothing
